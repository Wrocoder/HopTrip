# HopTrip: промпт для последовательного выполнения задач

Использование: передай этот файл кодовому агенту, у которого открыт репозиторий HopTrip. Команда «Начни с HT-00» запускает первичное изучение проекта. Затем отправляй «Выполни HT-01» или «Следующая задача». Все инструкции ниже адресованы этому агенту.

---

## Роль и цель

Ты работаешь с существующим проектом HopTrip — https://hoptrip.pl/.
Помоги последовательно улучшить UI/UX, удержание пользователей, привлечение аудитории и монетизацию. Реализуй изменения в существующем проекте, сохраняя его архитектуру и рабочие интеграции.

Продуктовая цель: помочь человеку выбрать короткую поездку из Польши с учётом цены перелёта, полного бюджета и удобства путешествия.

Стартовая аудитория для проверки гипотезы: жители Вроцлава, рассматривающие поездки на 2–4 дня. Существующие предложения из других аэропортов сохраняются.

Приоритеты: работающий поиск → понятное предложение → измерение переходов → сохранение поездки и возвращение пользователя → продвижение → подтверждённый доход.

## Обязательный режим: одна задача за один запуск

1. Выполняй только одну задачу с указанным ID. Не запускай весь список, не объединяй соседние задачи и не переходи к следующей автоматически.
2. Если я передал этот документ без номера задачи, выполни только HT-00.
3. Команда «Следующая задача» означает: прочитать журнал прогресса, найти первую незавершённую задачу по порядку ID, зависимости которой выполнены, и выполнить только её. Если текущая задача IN_PROGRESS, сначала продолжить её.
4. Если задача уже реализована, проверь соответствие критериям и зафиксируй результат; не переписывай рабочий код ради формального изменения. После этого остановись.
5. Если обязательная зависимость не выполнена, объясни, какой ID нужен. Не реализуй зависимость вместе с выбранной задачей.
6. Внутри выбранной задачи самостоятельно выполняй обратимые локальные действия: изучение кода, реализацию, проверку, исправление обнаруженной регрессии. Не спрашивай разрешение на каждый шаг.
7. Если выполнение невозможно без доступа, недоступных данных или существенного продуктового решения, выполни доступную часть, зафиксируй точный блокер и задай один конкретный вопрос. Неполную реализацию не отмечай DONE.
8. По окончании выдай отчёт по выбранной задаче и остановись. Название следующей задачи — только рекомендация для следующей команды.

## Общие правила реализации

- Сначала прочитай AGENTS.md, README, инструкции проекта, структуру приложения и текущие изменения Git. Сохраняй чужие незавершённые изменения.
- Используй существующие стек, компоненты, стили, интеграции и инфраструктуру. Не проводи сопутствующий рефакторинг всего приложения.
- Пользовательский интерфейс — на естественном польском; отчёты для меня — на русском.
- Сохрани зелёно-кремовую палитру и узнаваемость бренда. Новые элементы должны следовать текущим дизайн-токенам.
- Отделяй цену перелёта от бюджета поездки, сумму на человека от суммы группы, сохранённую цену от проверки на стороне продавца. Пустое значение расхода — неизвестный расход, а не ноль.
- Время рейсов, багаж, цены, отели и события должны происходить из доступных источников. Не заполняй production вымышленными предложениями. Демо-данные допустимы только в явно обозначенных локальных примерах и тестах.
- Метка «проверено» должна соответствовать реально выполненной проверке. Время записи кэша не выдавай за время проверки наличия билета.
- Сохраняй существующие согласия на аналитику и маркетинг, возможность отписки, партнёрские обозначения и защиту секретов. Не обходи их для увеличения конверсии.
- Эта работа по умолчанию включает код, локальное тестирование и черновики. Продакшен-деплой, применение миграций в production, включение реальных рассылок, публикации, отправка сообщений и подключение платежей требуют отдельного явного поручения. Не выполняй их автоматически вместе с задачей.
- Если задача требует миграции, подготовь её в принятом формате и проверяй только в локальной/тестовой среде. Не изменяй реальные пользовательские данные ради проверки.
- Проверки должны соответствовать риску: регрессионные тесты для поиска, расчётов, пагинации, подписок и переходов; визуальная проверка для вёрстки и текстов. Не добавляй тесты, которые лишь повторяют реализацию.
- Если внешний источник или инструмент недоступен, честно укажи, что именно не проверено. Заглушку или просмотр кода не выдавай за успешную внешнюю интеграцию.

## Формат работы над выбранной задачей

Перед изменениями коротко сообщи: ID, найденное текущее поведение, план из 3–5 шагов. Затем реализуй и проверь задачу без дополнительного согласования обычных локальных действий.

Итоговый отчёт:

1. ID и статус.
2. Что изменилось для пользователя или бизнеса.
3. Какие файлы изменены.
4. Как проверено, включая ручной сценарий воспроизведения при необходимости.
5. Ограничения и что ещё требует внешнего доступа или отдельного запуска.
6. Обновление журнала и рекомендуемый следующий ID. Не выполняй его.

## Задачи

### HT-00. Изучить проект и зафиксировать исходное состояние

Найди реализацию главной, поиска, карточки предложения, калькулятора, справочников городов, партнёрских переходов, аналитики, SEO и существующих уведомлений. Определи источники цен, доступные поля расписания, способы локального запуска и проверки.

Проверь наблюдения аудита. Зафиксируй, что уже реализовано, что воспроизводится и что требует доступа. Создай журнал с 25 ID и документ `docs/hoptrip-baseline.md` либо используй принятые аналоги.

**Готово, когда:** описаны реальные компоненты и ограничения, указан воспроизводимый способ запуска, журнал создан. На этой задаче допускаются только изменения документации; код приложения не меняй.

### HT-01. Исправить поиск направлений и добавить подсказки

Определи причину ошибки `Milan` / `milan`. Сделай выбор направления с подсказками на основе справочника, используя подход, уже работающий для аэропорта вылета.

Раздели отображаемое польское название и внутренний идентификатор. Поддержи регистр, лишние пробелы, английские и польские названия известных городов; IATA-коды — когда соответствие однозначно. Не сопоставляй неизвестный ввод с произвольным городом. Сохрани ранее работающие URL.

**Готово, когда:** `milan`, `Milan`, ` MILAN ` и `Mediolan` приводят к одному направлению; неизвестное значение получает понятную подсказку; пустое поле сохраняет смысл «любое направление». Бюджет и остальные фильтры не сбрасываются. Есть регрессионные проверки нормализации и разрешения алиасов.

### HT-02. Уточнить даты и добавить быстрые фильтры поездок

Явно обозначь диапазон возможных дат вылета и отдельно длительность пребывания. Добавь пресеты «Na weekend», «2–3 noce», «Loty do 300 zł» без изменения смысла существующих фильтров.

Для каждого пресета зафиксируй правила и покажи их в интерфейсе. Например, календарные выходные — вылет в пятницу/субботу, возврат в воскресенье; такой фильтр без часов рейсов не обещает поездку без отпуска. Используй Europe/Warsaw для относительных дат.

**Готово, когда:** пресеты применяются и снимаются, параметры сохраняются в URL, даты проходят валидацию, после возврата назад фильтры восстанавливаются. Правила не противоречат показанным предложениям.

### HT-03. Привести названия и форматы к польской локали

Используй единый слой отображения городов: Warszawa, Wrocław, Poznań, Mediolan и остальные поддерживаемые названия. Приведи пользовательские даты и суммы к согласованным польским форматам, добавь дни недели и количество ночей.

Не переименовывай внутренние ключи, существующие адреса страниц и параметры партнёров только ради отображаемого текста. Учти склонения в заголовках и подписи аэропортов WAW/WMI.

**Готово, когда:** главная, выдача, карточка, калькулятор и посадочные страницы используют согласованные названия; нет сломанных ссылок и потери различий между аэропортами.

### HT-04. Настроить измерение ключевых действий

Сначала выясни, какие события уже собираются. В рамках текущей аналитики добавь недостающие: отправка поиска, результат поиска с числом предложений/ошибкой, открытие предложения, переход к партнёру с категорией flight/stay/activity. Для будущих функций опиши события сохранения поездки и подтверждения подписки; отправлять их должны только реально существующие действия.

Зафиксируй контракт полей: анонимный контекст в пределах существующего согласия, ID предложения, тип партнёра, применённые фильтры и разрешённые метки кампании. Исключи дублирование при повторном рендере. Не передавай email, токены подписки и секреты в аналитику.

**Готово, когда:** основные события проверены в тестовой/отладочной среде, отказ от необязательной аналитики соблюдается, определения метрик документированы. Факт установки события не подменяет наличие собранной статистики.

### HT-05. Проверить партнёрские переходы и атрибуцию

Проверь существующие Aviasales, Stay22 и Tiqets: маршрут, даты, число гостей, валюту, локаль при поддержке, партнёрский идентификатор и разрешённые параметры кампаний. Исключи повторное оборачивание ссылок разными механизмами.

У кнопки перелёта покажи понятное действие и фактического партнёра. Сохрани disclosure. Для неработающей/неактивной интеграции показывай корректное состояние, без ложного обещания бронирования. Не заявляй точную цену после перехода.

**Готово, когда:** тестовые переходы ведут к правильному предложению/поиску; описан способ проверки кликов и продаж в кабинете. Если кабинета нет, отдельно укажи: проверены параметры и переход, начисление комиссии не подтверждено. Покупки для теста не совершай.

### HT-06. Сделать карточку перелёта информативнее

Покажи рядом с ценой даты, дни недели, ночи, известные аэропорты и перевозчика. Время вылета/прилёта обоих плеч, пересадки и багаж показывай только при наличии достоверных полей источника. Отличай код города от конкретного аэропорта.

Для отсутствующих сведений используй короткие подписи «Godziny do sprawdzenia u partnera» и аналогичные. Если расписание есть, рассчитывай интервал между прибытием и обратным вылетом с учётом локальных часовых поясов; не называй его временем прогулок по городу.

**Готово, когда:** цена за человека и туда-обратно читается однозначно; известные ограничения видны до перехода; покрытие данными и пробелы описаны; неизвестное не выглядит подтверждённым. Новую большую интеграцию ради расписания в эту задачу не включай — зафиксируй её необходимость отдельно.

### HT-07. Уплотнить первый экран главной

Сохрани текущую палитру и типографическую основу. Уменьши вводный блок, сократи лишние отступы, сформулируй понятную пользу продукта. Порядок: компактный поиск → быстрые фильтры → актуальные предложения выбранного аэропорта → дальнейшее планирование.

Подписку показывай здесь только когда она реально реализована. Фотографии направлений допустимы из разрешённого источника, с заданными размерами и без тяжёлой загрузки. Проверь, что баннер приватности не перекрывает основной сценарий; технические подробности можно перенести в раскрываемую часть, сохранив сами варианты выбора.

**Готово, когда:** предложения появляются существенно раньше по сравнению с исходным экраном, основное действие понятно, поиск и согласия продолжают работать. Приложи сравнение до/после на одинаковом размере окна.

### HT-08. Добавить сортировку, количество и состояния выдачи

Покажи количество результатов и добавь сортировки по цене, ближайшей дате и действующей оценке выгодности. Сортировать нужно всю подходящую выборку до пагинации, с устойчивым порядком для одинаковых значений.

Храни сортировку и фильтры в URL. Раздели состояния загрузки, отсутствия предложений, неверного ввода и ошибки источника. При пустой выдаче предложи снять конкретное ограничение, но не изменяй фильтры молча.

**Готово, когда:** счётчик соответствует той же выборке, порядок верен между страницами, изменение фильтра сбрасывает неподходящую позицию пагинации, повторное открытие URL восстанавливает выдачу.

### HT-09. Сделать оценку цены и свежесть понятнее

Перенеси акцент с абстрактных баллов на краткое объяснение цены относительно сравнимых наблюдений. Подпиши баллы как оценку ценового предложения. Сложный расчёт оставь в раскрывающемся блоке.

Отдельно показывай свежесть и достаточность данных. Не меняй математическую модель в рамках визуальной задачи и не превращай существующий балл в оценку комфорта. При недостаточных данных показывай предварительную оценку/ограничение. Не генерируй скидку без подходящей базы сравнения.

**Готово, когда:** основное объяснение подтверждается исходными данными, методология доступна, дата сохранения отличается от проверки на стороне продавца, существующие расчёты не изменились неожиданно.

### HT-10. Упростить и сохранять расчёт бюджета

Сделай основные расходы заметнее: перелёт, жильё, трансферы и питание. Дополнительные статьи можно свернуть. Сохрани имеющиеся подсказки по транспорту и источники тарифов.

Сохраняй черновик подходящим существующей архитектуре способом, восстанавливай после обновления, предложи явный сброс. Различай бюджеты разных поездок; при изменении дат и состава группы обозначай суммы, требующие перепроверки. Не подставляй произвольные цены жилья и питания.

**Готово, когда:** корректно работают расчёты на человека/группу, за ночь/период, ноль/неизвестно, восстановление и сброс. Подтверждены сценарии одной и нескольких персон, смены дат и неполного бюджета. Текст об удалении расчёта соответствует новому поведению.

### HT-11. Сохранять поездку и делиться ею

Сохраняй выбранное предложение, даты, людей и бюджет. Реализуй «Zapisz wyjazd» и «Udostępnij» без обязательного создания аккаунта, если существующая архитектура это позволяет. Общая ссылка должна открываться у другого человека; localStorage сам по себе для этого недостаточен.

Получатель видит понятную копию/представление поездки; его изменения не должны незаметно менять план автора. Не включай в публичный URL контакты, токены управления подпиской или приватные заметки. Подпиши сохранённую цену и предупреди о необходимости проверить её заново.

**Готово, когда:** поездка переживает обновление, ссылка работает в отдельной сессии, устаревшая/недоступная оферта имеет понятное состояние, превью содержит корректные город и даты без ложной актуальности цены.

### HT-12. Создать настройку персональной подписки

Проверь существующий бот/подписки. Реализуй минимальные настройки: аэропорт, максимальный бюджет на перелёт, диапазон ночей, удобные даты/выходные и частота. Начни с одного реально доступного канала доставки, используя существующую инфраструктуру.

Объясни пользу подписки. Предусмотри подтверждение владения каналом, изменение настроек и отписку. Email при необходимости подтверждай; для Telegram используй подтверждённый chat_id после действия пользователя в боте, а не username. До завершения подтверждения не показывай подписку как активную.

**Готово, когда:** подписка сохраняется, повторная регистрация не создаёт дубли, настройки изменяются, отписка работает, статусы понятны. Если нет провайдера/токена, укажи блокер; не делай неработающую кнопку. Массовая отправка не входит в задачу.

### HT-13. Подготовить персональные подборки и уведомления

Реализуй формирование еженедельной подборки для настроек пользователя; для первой версии достаточно до пяти подходящих предложений. При отсутствии совпадений не добавляй неподходящие варианты ради заполнения.

Добавь исключение дублей, идемпотентность повторного запуска, ограничение частоты и рабочую отписку. Используй шаблон с маршрутом, датами, ночами, наблюдаемой ценой, известными ограничениями и ссылкой на поездку. Запускать по расписанию в Europe/Warsaw; время расписания вынеси в настройку.

**Готово, когда:** на фикстурах и тестовом транспорте формируется корректная подборка, повторный запуск не дублирует сообщения, отписавшиеся исключены. Для срочных уведомлений подготовь расширение только если оно помещается в текущую архитектуру; не обещай пользователям недоступную функцию. Реальные отправки и включение production-расписания выполняются отдельной командой.

### HT-14. Улучшить сценарий поиска жилья

В существующем блоке жилья сделай действие понятным: найти жильё в конкретном городе на выбранные даты. Сохраняй город, check-in/check-out и число гостей при переходе. Учитывай доступные сведения о дате прибытия, а при их отсутствии давай изменить даты вручную.

Сохрани партнёрское обозначение и возможность добавить выбранную пользователем стоимость в бюджет. Показывать реальные варианты жилья можно только при наличии разрешённой интеграции; не придумывай карточки и цены. Не обещай автоматический возврат стоимости из внешнего сайта без такой возможности.

**Готово, когда:** изменённые даты и число гостей передаются, видна самостоятельность бронирования жилья, переход измеряется, поля бюджета заполняются однозначно.

### HT-15. Улучшить подбор достопримечательностей

Доработай существующие Tiqets/другие доступные предложения на одном пилотном направлении. Покажи несколько подходящих вариантов: что это, кому интересно, ориентировочная длительность при наличии источника и действие для проверки билетов. Добавь полезные бесплатные варианты при наличии проверенной информации.

Не утверждай, что билет доступен в даты поездки, если источник этого не подтверждает. Цены, варианты входа и ограничения должны быть взяты из источника. Сохрани афилиатные обозначения и возможность учесть расход в бюджете.

**Готово, когда:** нет нерелевантного списка ради комиссии, ссылки ведут к нужным объектам, доступность и стоимость обозначены честно, переходы измеряются.

### HT-16. Проверить и исправить мобильный сценарий

Пройди поиск → выдачу → предложение → бюджет → партнёра на ширинах 360, 390 и 768 px и сравни с десктопом. Проверь формы, календарь, длинные названия, фильтры, баннер приватности, экранную клавиатуру и доступность управления с клавиатуры.

Исправь обнаруженные проблемы. При необходимости добавь закреплённую кнопку проверки цены, которая не перекрывает контент и нижние системные зоны. Проверь подписи элементов, фокус и понятность ошибок. Производительность измеряй доступным инструментом; лабораторные результаты не называй полевыми данными пользователей.

**Готово, когда:** сценарий полностью проходим, нет горизонтальной прокрутки и перекрытий, подготовлены скриншоты и перечень проверок. Не выдумывай результаты Lighthouse/Core Web Vitals.

### HT-17. Проверить техническую основу SEO

Проверь фактические title, description, canonical, sitemap, robots, статус-коды, внутренние ссылки и доступность значимого контента для обхода. Определи отдельно полезные посадочные страницы и произвольные сочетания фильтров.

Реализуй согласованную политику индексирования, избегая конфликтов robots/noindex/canonical. Сохрани действующие URLs, если нет обоснованной причины миграции. Для истёкших предложений выбери поведение по их полезности и не маскируй исчезнувшую цену как актуальную.

**Готово, когда:** проверки выполнены на реальных типах страниц, нет массового закрытия полезного контента, sitemap и canonical соответствуют выбранной политике. Без Search Console не заявляй, что индексирование или позиции улучшились.

### HT-18. Улучшить посадочную страницу вылетов из Вроцлава

Доработай существующую страницу `/from/WRO`, если она остаётся канонической. Сделай понятный польский заголовок, доступ к фильтрам, актуальные поездки и полезные ссылки на аэропорт, бюджет и путеводители.

Добавь небольшой оригинальный блок, отвечающий на задачу короткого выезда из Вроцлава. Размести полезную навигацию до бесконечного списка карточек. Не создавай дубликаты только ради разных формулировок ключевых слов.

**Готово, когда:** страница помогает выбрать поездку, внутренние ссылки рабочие, текст согласован с данными, поисковые метаданные конкретны. Дополнительные города оставь на следующие отдельные поручения.

### HT-19. Подготовить одну кампанию продвижения

Подготовь пакет для аудитории Вроцлава: одну недельную подборку, одну карусель, сценарий одного короткого видео и одно сообщение администратору подходящего сообщества. Всё — на польском, с единым предложением пользы.

Используй актуально проверенные предложения с датой проверки и прямыми ссылками. Если доступ к данным отсутствует, подготовь явный шаблон с незаполненными полями; не подставляй вымышленные цены. Для каналов определи согласованные UTM-метки и метрики кампании.

**Готово, когда:** материалы готовы к рассмотрению, указаны канал, аудитория, призыв к действию, метки и способ оценки. Проверено, что целевые страницы и обещанные функции работают. Ничего не публикуй и никому не отправляй.

### HT-20. Собрать отчёт о воронке и доходе

На основе HT-04/05 подготовь минимальный отчёт средствами, уже принятыми в проекте. Определи знаменатели метрик: успешный поиск, просмотр предложения, переход к партнёру, возвращение за 7/30 дней, подтверждённая комиссия на 1 000 посещений. Разделяй партнёров и кампании.

Различай клик, бронирование, подтверждённую комиссию и фактическую выплату. Учитывай отмены и задержку подтверждения. Для ретеншена используй только доступный и разрешённый способ идентификации; при его отсутствии прямо обозначь ограничение. Не считай отсутствующие данные нулём.

**Готово, когда:** формулы, источники, период и ограничения документированы, доступные реальные данные сведены, недоступные показатели отмечены. Прогнозные сценарии отделены от фактического дохода; новый сложный BI-продукт ради отчёта не создаётся.

### HT-21. Проверить источник событий для одного города

Выбери один город с достаточным количеством предложений HopTrip. Проверь доступные официальные источники, начиная с Ticketmaster Discovery API: актуальные условия доступа, ограничения, поля даты/времени, географию, статусы отмены/переноса и наличие реальных событий.

Проведи небольшую проверку с реальным ответом, если есть разрешённый доступ. Зафиксируй пример схемы, качество покрытия и способ связи с городом и датами поездки. Отсутствие ключа не компенсируй выдуманными ответами.

**Готово, когда:** есть обоснованное решение о пригодности источника для пилота и описаны ограничения. Если пригодность не подтверждена, HT-22 остаётся заблокированной. В этой задаче production-интеграцию не добавляй.

### HT-22. Добавить события в даты поездки для пилотного города

Используй решение HT-21. Добавь блок событий, соответствующих месту и датам поездки. Учитывай локальный часовой пояс события, известное расписание рейсов, отмены, переносы, дубли и свежесть кэша. Если часы рейсов неизвестны, обозначь необходимость проверить совместимость.

Сохрани ссылку на первоисточник и отдельную проверку билетов. При отсутствии событий блок должен спокойно исчезать или показывать полезное пустое состояние. Ошибка API не должна ломать страницу перелёта.

**Готово, когда:** интеграция ограничена пилотным городом и управляется конфигурацией, даты и статусы проверены, события не выданы за гарантированно доступные билеты, сбой источника обработан.

### HT-23. Подготовить проверку спроса на платные уведомления

Используй реальные результаты HT-13/20. Предложи один небольшой платный пакет: например, несколько аэропортов, дополнительные условия расписания и приоритетные уведомления — только для реализуемых возможностей.

Подготовь гипотезу цены, предложение для пользователя, макет/черновик страницы интереса, способ измерения и критерии принятия решения. Значение 19 zł/месяц можно рассматривать лишь как тестовую гипотезу, а не установленный тариф. Сбор интереса должен честно объяснять, что функция ещё проверяется и оплаты нет.

**Готово, когда:** описаны состав пакета, аудитория, сигнал спроса и ограничения данных. Нет активных платежей, фиктивной покупки и обещаний недоступных функций. Публикация эксперимента и включение оплаты — отдельные задачи.

### HT-24. Подготовить предложение спонсору подборки

На основе подтверждённых метрик подготовь краткий польский media kit: аудитория, формат размещения, реальный охват, доступные показатели переходов, маркировка рекламы и условия измерения результата.

Предложи один пилотный формат для релевантного партнёра, например размещение в подборке из Вроцлава. Цена и возможный эффект — обоснованная гипотеза, без гарантий продаж. Если данных недостаточно, зафиксируй необходимые показатели; не выдумывай размер аудитории и кейсы.

**Готово, когда:** есть конкретное предложение для рассмотрения и честные ограничения. Письма, публикации и соглашения не отправлены и не заключены.
