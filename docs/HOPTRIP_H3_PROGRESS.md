## Правила чтения статусов

Статус работы: `TODO / IN_PROGRESS / BLOCKED / DONE / NOT_APPLICABLE`. Наличие уже работающего основания отражено отдельно; TODO не означает «всё отсутствует». DONE требует полного acceptance и доказательств. После H3-15:15 задач DONE (01–13/15/16),0 TODO,2 IN_PROGRESS (17/18), H3-14 BLOCKED по внешнему запуску.

Статус гипотезы: `CONFIRMED` — подтверждено кодом/тестом с указанным уровнем; `PARTIAL` — проблема лишь частична; `NOT REPRODUCED` — есть встречное доказательство; `NEEDS EVIDENCE` — недостаточно данных. Статический обзор не выдаётся за визуальный или production-аудит.

Implementation PR/commit H3: **нет**. Строки TODO описывают исходный аудит и существующее покрытие; актуальные изменения и новые прогоны указаны явно в строках IN_PROGRESS и журналах ниже. ## Подтверждённые воспроизведения

**A — календарный weekend пропускает возвращение в понедельник.** Одноразовый Python probe, SQLite `sqlite://`, `Base.metadata.create_all`, `helpers.catalog_fixture`; ни production DB, ни файловая DB не использовались. Создан synthetic ROUND_TRIP: WRO→BCN, пятница 2030-05-03 10:00 +02, обратный вылет воскресенье 2030-05-05 23:00 +02, прямой обратный рейс 120 минут. `list_deals(...weekend=True...)` вернул 1 предложение; `flight_facts.return_arrival=2030-05-05T23:00:00+00:00`, `return_destination_timezone=Europe/Warsaw`, то есть понедельник 06.05 01:00 local. Нет ошибки UTC-арифметики: фильтр использует даты вылетов. Это основание для нового режима H3-01, а не разрешение незаметно менять старый weekend. Код UI умеет показать `+1 dzień`; визуальная видимость в этом запуске не подтверждена.

**B — missing history может стоять выше CURRENT.** `score_flight_deal` с одинаковыми `observed_at=now=2030-01-01T00:00:00Z`, `expires_at=None`: current=100, median=None, samples=0 → **45 PROVISIONAL**; current=200, median=100, samples=5 → **19 CURRENT**. `_deal_order` сортирует score DESC. Это воспроизводимое следствие neutral price score=50 и весов, а не SQL NULL issue. Нельзя автоматически объявить такую выдачу багом формулы: требуется определить продуктовую политику сравнения eligible/provisional.

**C — двусмысленный lodging label и технический sort.** `catalog.tsx` без проверки nights выводит `Bez noclegu · bagaż do sprawdzenia`; `filters.tsx` использует `Wynik pomocniczy ↓`, API default `score`. Подтверждение статическое, не новый screenshot.

**D — уже исправленные/частично решённые гипотезы.** Прошедшие tests подтверждают return-leg validation, отсутствие вычисления layover arrival из airborne duration, DST/invalid-clock guards, event-before-arrival/after-return conflicts, missing-history neutral copy, unknown-budget ≠ explicit zero, сохранение/валидацию локальных снимков. Это не полная проверка production UI.

REST `return_at` означает обратный вылет; GraphQL одноимённое поле — прилёт домой. `validated_segments` проверяет соответствие ticket/price/airports/times; разные источники нельзя механически объединять.
