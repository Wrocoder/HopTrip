## Первый шаг владельца

1. Открыть [регистрацию Developer Portal](https://developer-account.ticketmaster.com/user/register).
   Указать реальные имя и контактные данные, проект HopTrip, сайт https://hoptrip.pl.
   Не подставлять Travelpayouts marker в Ticketmaster Affiliate ID: это разные системы.
2. Ознакомиться с условиями, завершить регистрацию и вход. По официальному
   [руководству](https://developer.ticketmaster.com/products-and-docs/tutorials/events-search/search_events_with_discovery_api.html)
   приложение создаётся при регистрации; его Consumer Key используется как API Key.
   Если приложение/ключ не появились, обратиться в Developer Support через
   [Contact Us](https://developer.ticketmaster.com/support/contact-us/).
3. Сохранить ключ в отдельном локальном файле вне Git, например
   `C:\Users\DmitriyKiselev\.hoptrip\ticketmaster-api-key.txt` (только значение ключа).
   Сообщить помощнику путь, а не содержимое. Этот файл владелец создаёт самостоятельно.
   Не добавлять ключ к URL в чате, скриншоты или диагностические журналы.
4. Для коммерческого запуска заполнить [Partner with us](https://developer.ticketmaster.com/partners/)
   по тексту ниже. Личные данные и принятие условий остаются за владельцем.

## Что подтверждено документацией

[Getting started](https://developer.ticketmaster.com/products-and-docs/apis/getting-started/)
описывает доступ к Discovery после получения ключа. Для поиска афиши не требуется
Partner Commerce API с продажей билетов внутри HopTrip.

[Discovery API](https://developer.ticketmaster.com/products-and-docs/apis/discovery-api/v2/)
поддерживает город/страну, категории, даты и пересечение интервалов.
Ключ передаётся в `apikey`; нельзя логировать полный URL запроса.
В документации указаны 5000 запросов в сутки, 5 запросов/с и предел глубокой
пагинации `size * page < 1000`. В [FAQ](https://developer.ticketmaster.com/support/faq/)
указаны 2 запроса/с: пилот ограничить одним запросом/с, учитывать 429 и лимит аккаунта.

FAQ описывает отдельное одобрение affiliate-программы и привязку Impact Publisher ID
к developer-аккаунту. Получение данных не подтверждает комиссию.

[Условия API](https://developer.ticketmaster.com/support/terms-of-use/), раздел
Licensed Uses and Restrictions, ограничивают получение дохода через использование API,
хранение контента разумным сроком и требуют удаления по запросу в течение 24 часов.
Практический вывод для HopTrip: запросить подтверждение нашего коммерческого сценария
и допустимого кеширования до публикации интеграции. Численный TTL условия не задают.

## Проверка после получения ключа

1. Один запрос Event Search с size=1: подтвердить авторизацию, не сохранять ключ в отчёте.
2. Для четырёх городов проверить ближайшие 90 дней, затем уникальные интервалы
   действующих round-trip предложений. Использовать city + countryCode и locale=*,
   проверять город площадки; для Milan учесть написание Milano. Пустой ответ может
   означать несовпадение названия. Соседние города не включать автоматически.
3. Отдельно считать музыку, спорт, выставки. Arts & Theatre не считать автоматически
   выставками: проверить классификацию и описание. Для длительных выставок использовать
   пересечение периода, а не только дату начала. Часовой пояс брать из данных площадки/
   события и проверять; дни прилёта/вылета не считать гарантированно свободными.
4. Собрать компактный отчёт: город, период, категория, количество, несколько ID/ссылок,
   доля записей с известными датой, временем, площадкой, статусом и ценой;
   отдельно доля поездок хотя бы с одним подходящим событием. Отсутствие цены допустимо.
5. Удалить отменённые и неопределённые по дате записи из подбора на конкретные даты;
   проверить переносы и дубли. Пустую выдачу описывать как отсутствие данных источника.
   Не объявлять полную выгрузку, если достигнут лимит страниц или бюджета запросов.

Критерий закрытия блокера: рабочий собственный доступ, проверяемый отчёт по реальным
датам перелётов, подтверждённые условия использования и явно обозначенные пробелы.
Для пилота предлагается минимум два города с релевантными событиями на реальные даты;
это ещё не выполнение полного требования по всем трём категориям. При пробеле по
выставкам нужен второй источник с разрешением на использование расписания.
Поставщика для него выбирать по конкретным непокрытым городам после замера.
