# V4-06 — карточки перелётов

**DONE локально, 2026-11-08**, Europe/Warsaw. Выполнение начато 2026-11-07. Проверена текущая рабочая копия после V4-05. Задача ограничена карточками; реорганизация страницы поездки V4-07 не выполнялась.

## Что изменено

Существующая карточка уже содержала направление, даты, цену, переход к деталям, сведения об актуальности, предупреждения и native disclosure. Добавлять вторую реализацию карточки не потребовалось.

- Добавлена длительность пути отдельно для прямого и обратного направлений, если доступны корректные departure/arrival instants с явным offset. Разница считается в UTC, включая пересадки между этими событиями, а не вычитанием локальных часов. Неполные минуты округляются вверх. Для расчётного прибытия сохраняется пометка `szac./est.` на соответствующем значении. При отсутствии/ошибке/обратном порядке часов либо CRITICAL_INCOMPLETE длительность не выводится; обратный маршрут не восстанавливается по прямому.
- Технический интервал «между прилётом и обратным вылетом» и пояснение окна 08:00–22:00 с условными буферами перенесены в существующий «Детали рейса и цены». Они остаются в server-rendered HTML и доступны через native details, включая вариант без JavaScript. Число ночей и индекс удобства модели остаются снаружи.
- Условия «цена за перелёт, жильё отдельно» и «багаж уточнить» собраны в один абзац. Цена за человека, тип маршрута, исходное наблюдение цены и предупреждение о проверке наличия у партнёра остаются видимыми.
- Ночные/ранние прилёты, недостаточное пребывание, последствия для отпуска, длинные/ночные/рискованные пересадки, airport change, неизвестная защита пересадки, неполные/критические данные и разные аэропорты обратного маршрута не спрятаны в disclosure. Пояснение методики отделено от самих предупреждений.

Не менялись цены, ranking/eligibility, API, сохранённые поездки, analytics events, consent, ссылки на детали и returnTo, партнёрские URL, SEO и контракты локализации. Новый короткий заголовок длительности добавлен сразу в PL/EN/RU/UK. Отдельный вид страницы поездки сохраняет прежние полный schedule и интервал пребывания.

## Измерение плотности

Перед изменениями выполнен `h3-card.spec.ts` в режиме baseline: **8/8 PASS**, 24 замера высоты — три состояния source quality × четыре языка × desktop/mobile. [Исходные метрики](before-metrics.json). Для повторного запуска используется тот же spec с `HOPTRIP_CARD_BASELINE`, который требует меньшей высоты каждой соответствующей закрытой карточки и сохраняет проверки существенных предупреждений.

Все **24/24** соответствующие карточки стали ниже на **15,41–98 px**, или **1,70–7,96%**. [Метрики после](after-metrics.json), [полная таблица сравнения](comparison.json). Desktop-примеры: English COMPLETE 845,14 → 808,73 px; PARTIAL 926,58 → 890,17 px; CRITICAL 1122,95 → 1045,95 px. [До](card-before-en.png) и [после](card-after-en.png): один и тот же PARTIAL fixture; между запусками в Warsaw сменилась дата отображения наблюдения цены, даты перелётов сохранились. Дополнительно просмотрены [RU при 390 px](card-after-ru-390.png) и сохранён [синтетический длинный текст при 320 px](card-long-ru-320.png); screenshots относятся к локальному dev runtime.

Это локальное измерение высоты карточек, а не доказательство роста конверсии, улучшения Core Web Vitals или результат исследования с пользователями. Критические карточки могут оставаться длиннее из-за обязательных предупреждений.
