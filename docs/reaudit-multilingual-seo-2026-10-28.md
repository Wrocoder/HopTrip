# Повторная проверка приложения и мультиязычного SEO

Проверены текущее рабочее дерево и https://hoptrip.pl. Изменений приложения и публикации не выполнялось.

## Подтверждённые ошибки

### P2: неверный год обрушает карточку поездки

На `/en/deals/flight-3922-2026-11-16` в поле начала поездки в блоке событий ввести `10000-01-01`. Chromium/Edge разрешает такой год в `input[type=date]`. В консоли возникает `RangeError: Invalid time value`, вся карточка заменяется сообщением `Could not load offers. Please try again shortly.`

Причина: `apps/web/src/app/components/trip-events.tsx`, функция `date` и отображение `date(draft.start)` / `date(draft.end)`. Форматирование непроверенной даты выполняется даже при `validEventDates(...) === false`. Поля бюджета и проживания используют тот же черновик, поэтому защиту нужно применять ко всем входам. Требуется безопасное форматирование и согласованная проверка допустимых дат; одной HTML-границы max недостаточно.

Снимок: `../.cache/reaudit-invalid-year.png`. Воспроизведено дважды на production в отдельном браузерном контексте.

### P2: ошибочная дата мешает восстановить весь бюджет

Независимое воспроизведение на `/en/info/trip-budget`: ввести 321 в стоимость жилья, затем `10000-01-01` в начало поездки, обновить страницу. Стоимость жилья становится пустой; интерфейс сообщает `Could not read the draft. Enter amounts again...`.

`TripDraftProvider.save` сохраняет непроверенную дату, но `readBudgetDraft` отклоняет весь объект при восстановлении. Пользователь теряет доступ через интерфейс ко всем ранее введённым суммам из-за одного поля. До следующей записи исходный объект может оставаться в localStorage: речь об отказе восстановления, а не о доказанном немедленном физическом удалении. Следует сохранять корректные части черновика и отдельно показывать ошибку даты.

Файлы: `apps/web/src/app/components/trip-draft.tsx`, `apps/web/src/lib/budget-draft.ts`.

### P3: штатный SEO-аудит не адаптирован к мультиязычности

`apps/web/scripts/audit-seo.mjs` ожидает 61 URL вместо актуальных 85, допускает только прежние польские пути и проверяет `data.lang === "pl"` для каждой страницы. Поэтому `npm run audit:seo` будет сообщать ошибки на корректных EN/RU/UK. Это дефект проверки, а не доказательство проблем индексирования.

## Ограничения перевода и навигации

- `/en`, `/ru`, `/uk` возвращают 404; главная `/` польская, без переключателя языка. В переводных разделах логотип ведёт на `/`, поэтому после перехода на главную пользователь снова видит польский интерфейс.
- Это соответствует текущему частичному rollout, но мешает восприятию сайта как полностью мультиязычного. Приоритет развития: перевод главной и основных SEO-посадочных по городам/маршрутам; затем путеводителей.
- Непереведённые материалы сейчас явно помечены как польские. Их отсутствие в языковом sitemap не следует исправлять добавлением несуществующих URL.

## Проверка опубликованного SEO

- Все 85 URL из sitemap: HTTP 200, один canonical, один h1, нет meta noindex.
- 24 языковых URL (8 страниц × EN/RU/UK): правильный html lang, canonical на собственный языковой URL, 5 alternate-ссылок (PL/EN/RU/UK/x-default). У опубликованных страниц из sitemap обратные hreflang-ссылки присутствуют.
- `/robots.txt` разрешает обход сайта и указывает `https://hoptrip.pl/sitemap.xml`; закрыты `/api/` и `/go/`.
- Просмотрены 9 production-страниц в Edge при ширине 390 px, включая каталог на трёх языках и реальную карточку. В обычном сценарии нет pageerror и горизонтального переполнения. Это выборочная проверка, не полный аудит доступности и не физический телефон.
- Доказательства: `../.cache/reaudit-seo.json`, `../.cache/reaudit-browser.json`; скрипт `../.cache/reaudit-20261028.cjs`.

## Google Search Console

Специально включать языки в Google не требуется. Domain property `hoptrip.pl` либо URL-prefix property `https://hoptrip.pl/` уже охватывает `/en/`, `/ru/`, `/uk/`. Отдельные properties языковых разделов нужны только для удобства отчётности, а не для разрешения индексирования.

1. В существующем property проверить Sitemaps → `https://hoptrip.pl/sitemap.xml`. Если не отправлен — отправить; если уже есть — проверить успешное чтение обновлённой карты.
2. Через URL Inspection проверить `/en/deals`, `/ru/deals`, `/uk/deals`, выполнить live test и запросить индексирование этих ключевых страниц.
3. Следить за Page indexing и Performance по префиксам языковых URL. Проверить, что Google выбирает canonical соответствующего языка.

Повторная DNS-верификация не нужна для каждого языка при уже подтверждённом подходящем property. Hreflang уже есть в HTML; дублировать его в XML обязательно не требуется. Индексирование и позиции не гарантируются: Google указывает срок обхода от нескольких дней до нескольких недель.

Доступ в личный Search Console не выполнялся: факт индексирования, выбранные Google canonical и поисковые показы данным аудитом не подтверждены.
