# План улучшений HopTrip по результатам проверки

Дата плана: 2026-10-07. Обновление: 2026-10-08. Выпуски 1–4 и код подписок
подготовлены локально; справочные расходы реализованы как пилот 6A.
Рассылка выключена до настройки SMTP; 6B ждёт подтверждённого поставщика жилья.
Подробности: [первый выпуск](search-first-release-2026-10-07.md) и
[продолжение](product-improvements-release-2026-10-08.md). На production не опубликовано.

Основание: семь замечаний пользователя, текущая рабочая копия проекта и
`events-coverage-2026-09-30.json`. Production в рамках подготовки плана повторно
не проверялся. В рабочей копии есть незакоммиченные изменения; перед реализацией
нужно зафиксировать границу каждого выпуска и сохранить существующую работу.

JSON событий содержит срез на 30 сентября: 356 предложений перелётов,
совпадения событий с поездками — Милан 79/80, Стокгольм 20/20, Осло 11/13,
Париж 0/13. У всех четырёх городов `withPrice = 0`; выдача Милана, Парижа и
Осло помечена `truncated`. Это не аудит семи UX-проблем и не актуальный прайс.
Не использовать отсутствующие цены событий как нулевые расходы. Исправление
покрытия событий — отдельная задача, не условие выпуска улучшений поиска.

## Порядок и ориентировочная трудоёмкость

Оценки — рабочие дни одного разработчика, включая целевые проверки; уточнить
после воспроизведения. Ожидание внешних доступов, редакционной подготовки и
индексации сюда не включено.

| Выпуск | Приоритет | Результат | Оценка | Зависимость |
| --- | --- | --- | --- | --- |
| 0 | P0 | Воспроизведение, исходные метрики, границы изменений | 0,5–1 день | Нет |
| 1 | P0 | Названия городов и подсказки аэропортов | 2–3 дня | 0 |
| 2 | P0 | Быстрый поиск на первом экране | 1–2 дня | 1 |
| 3 | P1 | Понятный переход к партнёру и проверенная локализация | 1–2 дня | 0, документация партнёра |
| 4 | P1 | Постоянные SEO-страницы и индивидуальные превью | 3–5 дней | 0, редакционный контент |
| 5 | P1 | Email-уведомления по параметрам поездки | 4–6 дней | 1, почтовый провайдер |
| 6A | P1 | Справочные расходы в калькуляторе | 2–3 дня | Проверенные источники расходов |
| 6B | P2 | Подбор жилья с контекстом поездки | 2–4 дня | Программа жилья и документация |

Итого: ориентировочно 15,5–26 рабочих дней. Первые полезные изменения —
выпуски 1–2. Выпуски 3, 4 и подготовка внешних доступов независимы от подписок.
Интеграция API реальных цен жилья в эту оценку не входит: её объём определяется
после получения условий и документации поставщика.

Готово: есть воспроизводимые сценарии и исходный отчёт; установлено, какие

## 1. Поиск по городу и коду аэропорта

Файлы: `apps/web/src/app/components/filters.tsx`, `apps/web/src/lib/api.ts`,
`apps/api/app/api/catalog.py`, схемы локаций; новый переиспользуемый AirportSelect
и сервис разрешения названий.

- Использовать `/api/v1/airports` как источник вариантов. Отображать
  `Wrocław — WRO`; хранить выбранный код отдельно от текста в поле.
- Добавить поиск без учёта регистра, пробелов по краям и польских диакритик,
  включая отдельное преобразование `ł → l`. Поддерживать явные алиасы.
- В обычной форме передавать канонический `origin=WRO`. При редактировании
  текста после выбора сбрасывать старый код, чтобы не искать скрыто по нему.
- На сервере поддержать прямые запросы с однозначным названием города;
  существующие запросы с IATA должны сохранить поведение. Неизвестное или
  неоднозначное название возвращает понятную ошибку, а не пустой массив.
- Для города с несколькими аэропортами показывать варианты и просить выбрать
  конкретный аэропорт. Поиск «все аэропорты города» оставить за границей MVP.
- Поддержать клавиатуру, Enter/Escape, подписи и озвучивание вариантов.
  Предусмотреть сбой загрузки справочника и отправку известного IATA.
- В каталоге разделить состояния: неверный ввод, нет совпадений, API недоступен.

Готово: на фиксированных данных `WRO`, `wro`, `Wrocław`, `Wroclaw` и название
с пробелами дают одинаковые предложения при 200 PLN; неизвестный город не
выглядит как отсутствие рейсов. Проверены прямой URL, API, возврат браузером,
смена выбранного аэропорта и клавиатурный сценарий.

## 4. Индексация и социальные превью

Файлы: страницы `deals`, `from/[iata_code]`, `destinations/[slug]`,
`deals/[slug]`, `layout.tsx`, `sitemap.ts`, `lib/share-image.tsx`,
`scripts/audit-seo.mjs`, `tests/catalog.spec.ts`.

- Ввести единый список подготовленных постоянных страниц и использовать его
  для metadata и sitemap. Пилот: `/from/WRO` и `/destinations/milan`.
- Подготовить полезный уникальный текст: доступные направления/аэропорты,
  особенности поездки, ссылки на существующие руководства, актуальная выдача.
  Не дублировать целиком статьи `/info/*`; назначение посадочной — выбор поездки.
- Принять следующую политику для MVP:

| URL | Планируемая политика |
| --- | --- |
| Подготовленные `/from/*` и `/destinations/*` | `index, follow`, собственный canonical, включение в sitemap |
| Неподготовленные посадочные | Сохранить `noindex, follow` |
| Чистый `/deals` | Открыть после подготовки полезной обзорной страницы и отдельных метаданных |
| `/deals` с фильтрами/пагинацией | `noindex, follow`, документированная нормализация canonical; не включать в sitemap |
| `/deals/[slug]` | В MVP сохранить `noindex, follow`; добавить индивидуальные превью |
| Несуществующий аэропорт/направление | HTTP 404 |

- Для canonical параметризованных страниц отдельно определить эквивалентные
  варианты; не считать разные выборки одинаковыми автоматически.
- При временном отсутствии предложений сохранять полезную постоянную посадочную
  и честное пустое состояние; не переключать её индексацию при каждом обновлении.
- Добавить отдельные title, description, OG и Twitter metadata для главной,
  каталога, аэропортов, направлений и предложений; абсолютные URL изображений.
- Расширить существующий генератор: направление, даты конкретной поездки,
  изображение города с разрешённым использованием и бренд; для постоянной
  посадочной не выдумывать даты. Предусмотреть фирменное изображение по умолчанию.
- На первом этапе не включать быстро устаревающую цену в картинку. Определить
  ключ и срок кеширования; удалённая/истёкшая поездка не должна давать HTTP 500.
- Обновить SEO-аудит и тесты, где текущий `noindex` является ожидаемым результатом.

Готово: политика подтверждена HTML и HTTP-заголовками; в sitemap только
разрешённые канонические URL; изображения доступны публично с правильным типом,
проверены превью минимум для WRO, Милана и конкретной поездки. Проверка Search
Console после выпуска — отдельный контроль; техническая готовность не обещает
фактическое включение страницы в индекс.

## 5. Уведомления о предложениях

Предлагаемый MVP: email, один аэропорт на подписку, максимальная цена перелёта
в PLN на человека, длительность в ночах; необязательный диапазон дат вылета.
Не чаще одного письма в сутки, только при наличии новых подходящих предложений.

- Добавить заметный CTA на главную, каталог, пустую выдачу и страницу аэропорта;
  подставлять текущие фильтры, показать критерии перед отправкой формы.
- Добавить таблицы подписок и отправок, миграцию, API создания, подтверждения,
  изменения параметров и отписки. Состояния: pending, active, unsubscribed.
- Использовать подтверждение email, токены ограниченного срока для подтверждения,
  управление и отписку без аккаунта. Хранить подтверждение согласия и ограничить
  частоту запросов; не включать адреса в обычные логи и аналитику.
- Подключить отправку через адаптер провайдера; подготовить домен отправителя,
  необходимые DNS-записи, обработку отказов доставки и отключение рассылки.
- Подбор выполнять по тем же доступным предложениям и правилам фильтрации,
  что каталог. Перед отправкой повторно проверять доступность; дедуплицировать
  отправки и обрабатывать повторы задания без повторных писем.
- Обновить пользовательские тексты и политику обработки данных под фактический
  поток. В письме — параметры подписки, дата проверки цены и ссылка отписки.

Готово: до подтверждения предложения не отправляются; совпадающее предложение
попадает в письмо, неподходящее/истёкшее — нет; повтор задания не дублирует письмо;
после отписки отправок нет. Проверить смену параметров и сбой провайдера.
До подключения доставки форма не должна обещать работающую подписку.

## 6A. Справочные расходы в калькуляторе

Файлы: `components/trip-budget-calculator.tsx`, `lib/trip-budget.ts`,
`lib/airport-transfers.ts`; новый каталог проверенных расходов по направлениям.

- Сохранить существующую подстановку перелёта и дат; добавить действие
  «Заполнить ориентировочные расходы» для выбранного направления.
- Начать с 2–3 направлений, для которых удастся проверить источники.
  Хранить сумму/диапазон, валюту, единицу расчёта, источник и дату проверки.
- Разделить расходы на человека/группу, ночь/день/поездку. Для конвертации в PLN
  явно учитывать курс и дату; не складывать разные валюты напрямую.
- Использовать проверенные данные трансфера с учётом фактического аэропорта,
  количества людей и направления поездки; добавить ориентиры питания и транспорта.
- Заполнять только после действия пользователя; не перезаписывать исправленные
  суммы молча. Позволять менять значения и видеть, какие из них справочные.
- Неизвестные и устаревшие данные оставлять явно неизвестными. Сохранять различие
  между нулём и отсутствием суммы; обозначать итог как неполный при пропусках.
- Для ONE_WAY не выводить длительность пребывания из даты вылета; дать пользователю
  задать её. Учесть однодневные поездки и количество ночей отдельно от дней расходов.

Готово: сумма рассчитывается в грошах; проверены группа, число ночей, валюты,
нулевые/неизвестные расходы и сохранение ручных правок. У справочных значений
видны источник и давность; их нельзя спутать с подтверждённой ценой бронирования.

## 6B. Жильё в контексте поездки

Файлы: `components/trip-accommodation.tsx`, `lib/accommodation-links.ts`,
карточка предложения и калькулятор.

- Выбрать одобренную программу и получить действующие ссылки/документацию.
  Продолжить уже подготовленный компонент жилья.
- Передавать город, даты заезда/выезда и гостей только если формат партнёра
  это поддерживает. Разрешить исправить даты: вылет и заселение могут различаться.
- Если доступна лишь ссылка на город, честно сообщать о выборе дат у партнёра.
  Не считать ссылку источником стоимости жилья.
- Дать понятный возврат к строке жилья в калькуляторе и ввод общей цены проживания
  с корректным преобразованием в используемую единицу расчёта.
- Автоматическую подстановку реальной стоимости жилья вынести во второй этап
  после подтверждения API-доступа; там отдельно определить налоги, сборы,
  размещение группы, доступность и срок действия цены.

Готово: рабочая ссылка открывает нужный город и поддерживаемый контекст;
проверены ROUND_TRIP, ONE_WAY и поездка без ночёвки. Без источника цены жильё
не попадает в итог как известная сумма.

## Проверки, выпуск и оценка результата

- Каждый выпуск — отдельный набор изменений с описанием, целевыми проверками
  и возможностью отката. Миграцию подписок выпускать совместимо с предыдущим API.
- Для поиска: API-тесты разрешения названий и Playwright-сценарий формы.
  Для SEO: существующий аудит и проверки metadata/sitemap. Для партнёра:
  тесты построения URL и ручная проверка конечного сайта. Для подписок:
  интеграционные тесты состояний и повторов. Для бюджета: арифметические
  unit-тесты и ключевые сценарии интерфейса.
- Выполнять стандартные проверки затронутых частей проекта; инструкции Next.js
  читать из установленного пакета перед изменением кода, Python-команды запускать
  через интерпретатор проекта. Для публичных форм проверить мобильную верстку
  и доступность клавиатурой.
- После каждого выпуска повторять его исходные сценарии на опубликованной версии.
  Отдельно фиксировать ошибки API, редиректов, отправки писем и генерации картинок.
- Сравнивать равные периоды: долю корректных поисков без результатов, переходы
  из hero в выдачу и из предложения к партнёру, подтверждение подписок,
  возвращения из писем и использование справочных расходов. Аналитические
  события собирать с учётом существующего согласия.
- SEO оценивать отдельно по обходу, индексации, показам и кликам подготовленных
  страниц; при текущем небольшом трафике не объявлять причинный эффект по нескольким
  визитам. Численные продуктовые цели установить после исходного замера.

## Внешние зависимости

Для первых двух выпусков внешние решения не нужны. Для полного завершения
понадобятся: подтверждённые возможности локализации Aviasales, почтовый провайдер
и настройка домена отправителя, программа жилья, источники справочных расходов
и изображения с разрешённым использованием. Их подготовку начать в выпуске 0;
они не должны задерживать исправление поиска и главной.
