# Полноценный обратный маршрут — пункт 2

## Источник и обнаруженная ошибка

Срез production в 18:26 UTC: 255 доступных поездок туда-обратно. REST
prices_for_dates передал return_at, duration_back и return_transfers во всех
255, но ни одного явного аэропорта возврата. Эти данные не терялись в HopTrip.
[Срез и адресная проверка](return-routes-20261026/before.json).

[Официальный GraphQL Data API](https://support.travelpayouts.com/hc/en-us/articles/4417975783314-Aviasales-GraphQL-for-access-to-Flights-Data-API)
доступен с существующим ключом. Интроспекция схемы и запрос с сервера подтверждают
prices_round_trip → segments → flight_legs: отдельные аэропорты, отправление,
прибытие, operating_carrier и flight_number. grouping=NONE сохраняет разные
билеты. Это кеш поисков, не live Search API; отдельный доступ для него не требовался.

У точно совпавшего flight-3672-2027-01-08 общее return_at равно 09:00 Warsaw —
прилёту домой, а реальный вылет LTN — 05:55 UTC. Прежний код принимал общее
return_at за обратное отправление, а затем прибавлял duration_back. Теперь
это поле без сегментов не становится подтверждённым временем вылета.

## Реализация

- Новая nullable JSON-колонка TravelOffer.route_details, миграция
  0016_flight_route_details. Исходный raw_payload и наблюдения цены не переписываются.
- Обогащение после ingestion, до генерации карточек, в существующем часовом
  pipeline. Выбираются свежие round-trip предложения PLN. Уже известные данные
  того же билета повторно не запрашиваются. Отдельный CLI для первой загрузки:
  python -m app.jobs.enrich_flight_routes.
- Группировка по аэропорту отправления, фильтр календарных дат вылета, пагинация
  до 5 × 1000 записей на группу, общий предел 35 запросов за проход. Интервал
  между запросами минимум 1,1 сек при официальном лимите 60 запросов/минуту.
  [Лимиты поставщика](https://support.travelpayouts.com/hc/en-us/articles/4402565416594-API-rate-limits).
- Сопоставление по одинаковым пути и непрозрачному идентификатору t выбранного
  билета. Он сравнивается как идентификатор и не декодируется в расписание.
  Дополнительно проверяются исходные timestamps, аэропорты туда, валюта и цена
  с допуском 0,50 PLN на округление REST (208,81 → 209), полнота двух направлений,
  последовательность времени, длительности и число пересадок.
- Общее return_at может соответствовать началу или концу обратного сегмента;
  часы берутся исключительно из его flight_legs. Для date-only, неполного,
  несовпавшего или некорректного ответа аэропорты/часы не выдумываются. При ошибке
  GraphQL текущие цены продолжают жить по своим TTL; результат содержит счётчики.
- API list/detail публикуют outbound_legs и return_legs с независимыми зонами,
  временем, перевозчиками и номерами. Сегменты дают реальные source timestamps;
  они не помечаются как рассчитанные из длительности. Без них сохраняются явные
  return_origin_airport/return_destination_airport, если источник их передал;
  время fallback допускается только из явного return_departure_at.
- Календарные даты и ночи используют обратное отправление в зоне его аэропорта,
  а не прилёт домой на следующие сутки. Проверка совместимости событий получает
  то же отправление. Старые сохранённые пользовательские планы не перезаписываются.
- UI предупреждает о другом аэропорте возврата, показывает перевозчиков каждого
  направления, а в подробностях пересадочного маршрута — отдельные рейсы.
  Для неизвестного аэропорта остаётся предупреждение перед планированием трансфера.

Цена, observed_at, fetched_at цены, expires_at, observation_key и история при
обогащении не обновляются. Партнёрский URL остаётся исходным выбранным билетом.
Токен и идентификатор билета не попадают в публичный FlightFacts или отчёт.
Обновление событий остаётся один раз в день; пользовательские уведомления не включаются.

## Проверки и выпуск

Регрессии покрывают STN туда / LTN обратно, смешанные W6/LO на возврате,
ночной прилёт домой, независимые зоны, позднее событие после реального вылета,
другой билет/дату/цену/валюту, повреждённые сегменты, старый payload и ошибки API.
Браузерные проверки: Chromium mobile — 6 passed, включая гидратацию;
Chromium desktop — 5 passed. Web unit — 76 passed, lint, TypeScript и build
успешны. Полный API-набор — 563 passed / 7 PostgreSQL skipped; ruff/mypy успешны.
PostgreSQL проверяется в CI.

Далее: CI, миграция, выпуск, первая загрузка деталей и измерение покрытия на сайте.
При несовпадении с GraphQL предложение остаётся с неизвестным обратным маршрутом;
полное покрытие кеша заранее не обещается. Живое наличие/цена этой работой не проверяются.
