# Полноценный обратный маршрут — пункт 2

## Источник

Срез production в 18:26 UTC: 255 доступных поездок туда-обратно, ни одного
явного аэропорта возврата в REST. Время обратного вылета, длительность и число
пересадок присутствуют. [Срез](return-routes-20261026/before.json).

[Официальный GraphQL Data API](https://support.travelpayouts.com/hc/en-us/articles/4417975783314-Aviasales-GraphQL-for-access-to-Flights-Data-API)
доступен с существующим ключом и возвращает prices_round_trip → segments →
flight_legs: отдельные аэропорты, отправление, прибытие, перевозчика и номер.
Это кеш поисков, не live Search API.

Контракты сверены на одних и тех же непрозрачных идентификаторах билета:
**REST return_at — обратное отправление; GraphQL return_at — прибытие домой.**
Сравнивать эти одноимённые поля друг с другом нельзя. В GraphQL сегмент возврата
содержит оба момента независимо. Для flight-3672-2027-01-08 это 05:55 UTC из LTN
и 09:00 Warsaw в WRO. Прежний вывод по одному полю GraphQL исправлен этой сверкой.
REST duration_to/back у пересадочных маршрутов может содержать только сумму
времени отдельных рейсов, без ожидания пересадок. Прибытие по ней не вычисляется.

## Реализация

- Nullable JSON TravelOffer.route_details, миграция 0016_flight_route_details.
  Исходный payload, цена, observation_key, время наблюдения/доставки цены,
  expires_at и история не меняются при обогащении.
- Сопоставление по одинаковым пути и непрозрачному идентификатору t выбранного
  билета. Он не декодируется в расписание. Дополнительно проверяются отправление,
  исходные аэропорты туда, валюта, разница PLN до 1 zł между представлениями того
  же билета, два полных направления, порядок времени и число пересадок.
- REST return_at сверяется с отправлением обратного сегмента, GraphQL return_at —
  с его прибытием. Длительность проверяется как полное время либо сумма рейсов;
  ожидание пересадок не теряется в конечном расписании. Номера и перевозчики
  каждого flight_leg независимы; времена с неизвестной зоной показываются в UTC.
- Часовой pipeline после ingestion и до генерации карточек обогащает свежие
  предложения PLN. Известные данные того же билета не запрашиваются повторно.
  Запрос содержит аэропорт отправления, город назначения и не более 5 дат вылета,
  страница — до 400 строк,
  не более 5 страниц на пакет и 35 запросов за проход. Ближние вылеты приоритетны.
  Пауза 1,1 сек между запросами соблюдает лимит 60/мин.
  [Лимиты поставщика](https://support.travelpayouts.com/hc/en-us/articles/4402565416594-API-rate-limits).
- Первая загрузка без нового сбора цен: python -m app.jobs.enrich_flight_routes.
  Ошибки GraphQL/неполный ответ дают счётчики и неизвестные данные, не новую цену
  и не подтверждение отсутствия билета. Неизвестные аэропорты не копируются из
  направления туда. При отсутствии сегментов известное REST-время вылета остаётся;
  прилёт из REST-длительности рассчитывается только при нуле пересадок.
- API list/detail публикуют outbound_legs / return_legs и прежние плоские поля.
  Прибытие из сегмента не помечается рассчитанным. Даты проживания/ночи используют
  обратное отправление в зоне его аэропорта, а не прибытие домой следующими сутками.
  События сравниваются с тем же обратным отправлением. Пользовательские сохранённые
  планы не перезаписываются; исходная партнёрская ссылка сохраняется.
- UI сообщает о другом аэропорте возврата, показывает отдельных перевозчиков и
  номера, а в подробностях пересадочного маршрута — каждый рейс. Для неизвестного
  аэропорта сохраняется предупреждение перед планированием трансфера.

интроспекцией. Он не заполнил маршруты; хеш всех полей предложений (кроме новой

пределы и различия временных полей. На реальном пакете 5 дат: HTTP 200,
400 строк, 9 точных совпадений — все 9 проходят итоговую проверку маршрута.

Далее: CI, выпуск исправленного обогащения, первая загрузка и замер покрытия.
При отсутствии точного совпадения неизвестность остаётся явной. Наличие мест и
совпадение текущей цены у продавца этой работой не подтверждаются. События
по-прежнему обновляются один раз в день; физический пункт 8 отложен владельцем.


## Покрытие и календарный offset

После PR #14 два прохода по широким группам дали 101 и 51 новый маршрут:
152 из 258 предложений. Все поля TravelOffer, кроме route_details, и все
PriceObservation до/после совпали по SHA-256. Запросы дополнительно сужены
по городу назначения, чтобы лимит не расходовался на билеты в другие города.
Фильтр по конкретному аэропорту назначения исключает open-jaw: проверенный
KRK → BGY / MXP → KRK отсутствует при AIRPORT=BGY, но точно находится при
CITY=MIL. Поэтому используется именно город, а аэропорты подтверждаются сегментами.

ISO offset сегмента сохраняется в публичном timestamp. Если справочник ещё не
знает IANA-зону аэропорта, календарь использует явный исходный offset, а часы
интерфейса остаются подписаны UTC. Регрессия проверяет 01:30 +03:00 следующего
дня, который потерялся бы при преждевременном переводе timestamp в UTC.
После изменения — 68 целевых API-тестов и ruff/mypy успешны; полный CI далее.


## Повтор ненайденных билетов

Успешный, но несовпавший или неполный поиск сохраняет только метаданные
INCONCLUSIVE в route_details на один час. Это не означает отсутствие билета
и не становится фактом расписания. Новые билеты с другим ticket_key проверяются
сразу; уже известные сегменты не заменяются неудачным поиском. Такая пауза
позволяет последующим проходам добирать другие направления в пределах 35 запросов.
Ошибки HTTP/GraphQL не превращаются в отрицательный результат.
Регрессия проверяет отсутствие запроса на 59-й минуте и повтор на точной границе часа.

Живой UI до финального добора: Edge, 320/1440 px, два реальных маршрута,
включая смену MXP → BGY и пересадочный возврат. Проверены аэропорты, время,
перевозчики/номера, отдельные сегменты, неизвестный аэропорт; JS/overflow — 0,
axe изменённых блоков расписания/сегментов — 0.
[Браузерный отчёт](return-routes-20261026/browser-check.json).
Расширенный axe дополнительно выявил существующий heading-order у h3
«Cena i aktualność» вне изменённого расписания; это остаётся для отложенной UI-проверки.
