Основной рынок таблицы — Польша, язык `pl`. Это география аудитории, а не география назначения; иностранные города остаются поездками из Польши. Существующие PL/EN/RU/UK версии сохраняются; интерес на EN/RU/UK отдельно не исследован, поэтому польские приоритеты на них автоматически не переносятся.

Проверены актуальные `catalog-pages.ts`, `growth-pages.ts`, `search-policy.ts`, guide mapping, нужные editorial records и существующие search-policy tests. [Инвентаризация SEO-04](../seo04/INVENTORY.md) переиспользуется как исходная карта, а [coverage.json](coverage.json) извлекается повторно из текущих модулей для всех целевых и связанных страниц. Фактическое наличие контента не означает найденный дефект: до подтверждения пробела переписывание не требуется.

Приоритеты **C1/C2/C3 относятся к исследованию контента**, а не к приоритетам задач мастер-плана. Внутри групп порядок практический; статистически точного ранжирования нет.

1. **C1, строки 1–2:** исторический внешний demand proxy + существующая полезная статья + прямой путь к продукту. Первая работа — измерить точные запросы и проверить актуальность, а не автоматически расширять статьи.
2. **C2, строки 3–7:** готовые origin/weekend/city-break сценарии. Релевантность подтверждена кодом; спрос остаётся неизвестным. Три origin opportunities дополнительно имеют проверенные примеры конкурентного контента. Сначала измеряем существующее покрытие.
3. **C3, строки 8–12:** точные суммы, сезонный вопрос, поездки на концерт и route pilot. Суммы 300/1000 zł выбраны как примеры намерения, не как найденные популярные запросы или доступные цены. Высокая продуктовая связь сама по себе не повышает уверенность в спросе.

Покрыты все focus areas: origin (3–5,12), weekend (6–7), budget (8–9), seasonal (1–2,10), event (11). Во всех строках есть страна/язык, intent, доступные demand indicators, сезонность с границами знания, competition, coverage, target URL, конкретная рекомендация с условием и business relevance. Последнее — качественная связь с поиском/лотом/планом, не оценка будущих конверсий.

## Безопасные границы реализации

- Сначала улучшается существующая страница, если данные показывают конкретный пробел. Новая страница допустима только после query-level проверки намерения, отсутствия подходящего покрытия и наличия самостоятельной полезной информации/источников. В этой задаче новые URL не предлагаются к публикации; массовая origin×city×budget×season генерация исключена.
- `/city-break` означает 2–4 ночи; `/tanie-loty-na-weekend` — вылет пятница/суббота с обратным вылетом в ближайшее воскресенье. Это не обещание отсутствия отпуска или возвращения домой до полуночи.
- Budget filter ограничивает цену **полёта на человека**. `/deals?budget=300` и другие filtered URLs остаются `noindex,follow` по существующей policy. Стоимость всей поездки требует ночёвок, трансферов, багажа и прочих составляющих; неизвестные расходы не заменяются нулём. Не обещаем готовые туры/пакеты до1000 zł.
- Warsaw продолжает различать WAW/WMI; Rome — CIA/FCO. Не меняются canonical/hreflang/robots/sitemap или существующая indexation остальных registry pages ради новой фразы.
- Event контент не получает выдуманных дат/билетов. Фактический API `/api/v1/deals/{slug}/events` требует существующее предложение, supported context и валидные даты. Новое датированное событие требует официального первичного источника и повторной проверки статуса; общего event-инвентаря города в задаче не создаём.
- Наличие поискового интереса не является доказательством offer availability, низкой цены или корректного flight fit. Empty/error/freshness warnings, affiliate attribution и consent остаются прежними.

## Как уточнить стратегию при появлении данных

Это протокол для следующего согласованного content review, не выполненный импорт и не запуск ANALYTICS/GROW.

1. В GSC выгрузить query/page/country/date/search type для verified property HopTrip: PL, web, последние полные 90 дней и сопоставимый период год назад, если доступен. Сохранить property, timezone, даты, фильтры, дату экспорта и ограничения privacy/aggregation. Сверять точный URL и locale; отсутствие строки не считать нулевым спросом.
2. Для каждой opportunity получить показы/клики/CTR/позицию по query→page, отделить бренд и device. Потенциальную каннибализацию проверять по фактическому распределению; наличие каталога и guide само по себе её не доказывает.
3. Trends: PL, web, фиксированные полные периоды 12 месяцев и несколько лет для сезонных кандидатов; сравнивать одинаковые term/topic и параметры. Экспортировать ряд и параметры, не сравнивать абсолютные значения отдельных нормализованных выгрузок. Отметить insufficient data, а не писать «спроса нет».
4. Keyword Planner при доступе владельца: PL, Polish, Google Search, полный диапазон месяцев; сохранить exact/close-variant scope, диапазоны объёмов и дату. Competition/CPC отражают рекламу, их нельзя переименовывать в organic SEO difficulty. Не запускать кампании ради этой проверки.
5. После обоснованного улучшения одной страницы сравнить полные 28 дней до/после (если достаточно данных), дополнительно сезонный comparable period и состав query/device. Это рабочее окно, не гарантия статистической значимости или причинного SEO-эффекта. При малой выборке сохранять неопределённость и не обещать рост. События продукта использовать только уже доступные и разрешённые consent, без новой tracking-реализации в SEO-05.
