# V4-11 — уведомления о ценах

Выполнение 2026-11-08. После V4-01–10 выбрана одна следующая задача — V4-11. Проверена существующая подсистема email/Telegram, без новой очереди, API или модели подписок. V4-12 не начинается.

## Исправление

У email был пробел в проверке согласия. `ACTIVE` и `confirmed_at` проверялись при подборе, но версия согласия не проверялась; после сохранения резерва проверялись только статус и фильтры. Поэтому запись с неизвестной версией согласия либо с отозванным после резервирования подтверждением могла дойти до SMTP. У Telegram соответствующие проверки уже были.

Теперь email требует **существующую текущую версию согласия и подтверждение** как перед резервированием, так и непосредственно перед формированием/отправкой digest. Невалидная запись не расходует слот при подборе; отзыв после резервирования переводит доставку в `CANCELLED`, отправитель не вызывается. Старые состояния не получают согласие автоматически. Значение `CONSENT_VERSION` не менялось. Для неподтверждённой или нераспознанной записи нужен новый явный opt-in через существующий жизненный цикл, а не ручная подстановка согласия в БД.

Общий test helper теперь записывает реальную константу версии вместо условного `test`. Проверки отказа используют заведомо неподдерживаемые значения отдельно. Четыре новые SQLite-регрессии **упали до исправления** и прошли после него. Два дополнительных PostgreSQL-сценария меняют согласие/подтверждение из другой сессии после commit резерва; отправка отменяется.

Из runtime изменён только [alert_digests.py](../../apps/api/app/services/alert_digests.py). Конфигурация, signup/confirm/manage/unsubscribe API, Telegram, модели, миграции, источники цен, тексты и локализация приложения сохранены.

Цена в уведомлении остаётся наблюдением, не подтверждённой ценой бронирования. Сохраняются оговорки о свежести, багаже, неизвестных пересадках и отдельных расходах на жильё/трансфер. Weekend не обещает поездку без отпуска. Email остаётся на польском с явным предупреждением об этом в EN/RU/UK-интерфейсе; Telegram имеет существующие четыре языка.

## Изолированный PostgreSQL

Использован уже имеющийся `postgres:16-alpine`, `--pull=never`, отдельный контейнер с labels задачи и tmpfs, только `127.0.0.1:54966`, БД `hoptrip_test`. [Параметры](postgres.json), [полный API summary](api-summary.json). Существующие миграции применены только к этой одноразовой БД до `0021_telegram_alerts`. Новые миграции не создавались. PG fixture проверяет имя БД, создаёт отдельные случайные схемы и удаляет их после тестов; после полного прогона оставшихся `test_*` схем — 0.

Перед очисткой сверены точный container ID и обе ownership labels. Контейнер остановлен и удалён; постоянный volume не создавался, tmpfs не сохраняется. [Протокол очистки](postgres-cleanup.json). Docker engine, чужие контейнеры и кэшированный image не менялись.

## Готовность и отдельная активация

Локальные проверки завершают разработку V4-11, но не активируют доставку. Defaults всех четырёх флагов остаются `false`; production-настройки не читались и не менялись. Важно: `telegram_enabled=true` уже позволяет ответы на запрошенные команды при `telegram_delivery_enabled=false`; этот режим тоже требует согласованной реальной активации.

Перед отдельной разрешённой активацией оператору нужны проверенные настройки реального SMTP/бота и отправителя, выбранный кандидат релиза, согласованные тестовые получатели, staging-проверка с явным opt-in, наблюдение за SENT/UNCERTAIN/CANCELLED и план остановки workers/регистрации. Результаты in-memory тестов не доказывают доставляемость реальной почты или доступность Telegram-аккаунта. Не отправляйте реальные сообщения в качестве обычного regression-теста. Подробные gates — в [readiness.json](readiness.json).

Миграций приложения, новых зависимостей, deploy, production DB, реальных отправок и платных интеграций в этом выполнении нет. WebKit, реальные устройства, ручной screen reader и field CWV не заявляются.
