# Ветки и публикация HopTrip

## Где находится код

| Ветка / тег | Назначение | Публикация |
| --- | --- | --- |
| `main` | Поиск, главная, SEO, превью, калькулятор, опубликованные путеводители и действующие интеграции | Автоматически после успешного CI |
| `feature/ticketmaster` | Афиша Ticketmaster: API, интерфейс и тесты | Не публикуется; нужны коммерческие условия |
| `feature/email-alerts` | Подписка, SMTP, подтверждение и отписка, worker и тесты | Не публикуется; нужны почтовый провайдер и проверка доставки |
| `feature/accommodation` | Блок жилья, пустой каталог одобренных ссылок | Не публикуется; требуется одобрение партнёра |
| `production-2026-10-09-before-split` | Снимок ручного выпуска 8–9 октября, включая выключенные функции | Исторический тег, не менять |
| `master` | Прежняя основная ветка; сохранена для истории | Автодеплоя нет, использовать `main` |

Код выключенных функций ранее был доставлен на сервер. Теперь он вынесен из `main`.
Миграция `0014_deal_alerts` и её модели остаются в `main`: схема уже применена,
удалять историю миграций или таблицы при разделении нельзя. Перед удалением обработчиков
рассылки серверный deploy проверяет, что таблица подписок пуста.
Старые документы описывают состояние на указанную в них дату; текущая карта — здесь.

Ветки функций основаны на `main`, каждая возвращает только свою реализацию.
Перед продолжением: `git switch feature/ticketmaster` (либо другая ветка),
`git merge origin/main`. После готовности — PR в `main`, проверки и merge.
При объединении нескольких функций возможны обычные конфликты общих imports/config;
сохранить обе интеграции и повторить полный CI. Не переносить целиком исторический тег
в `main`, иначе вернутся все выключенные функции сразу.

## Автодеплой

Workflow `.github/workflows/ci.yml`: каждый push запускает проверки; только успешный
push в `main` запускает job `deploy` с environment `production`.
PR и feature-ветки ничего не публикуют. Параллельные публикации блокируются в Actions
и через `flock` на сервере. Сервер дважды проверяет, что SHA всё ещё является HEAD `main`.

GitHub хранит отдельный ключ `DEPLOY_SSH_KEY` и проверенный `DEPLOY_KNOWN_HOSTS`;
переменные `DEPLOY_HOST` / `DEPLOY_USER` задают сервер. Ключ ограничен forced command:
принимается только SHA, shell, forwarding и SCP для этого ключа запрещены.
Секреты приложения остаются в `/opt/hoptrip/.env.production`, данные оператора —
в `/etc/hoptrip/operator.json`. В Git их нет.

Сервер скачивает архив указанного SHA публичного репозитория, собирает ARM64-образы,
выполняет preflight, останавливает writers, делает pg_dump и проверяет список восстановления,
применяет миграции, запускает API/web/worker и проверяет HTTPS. Caddy, DB и внешние
systemd-службы при этом не пересоздаются. Источники: `/opt/hoptrip/releases/<sha>-<time>`.
Текущая версия: `/opt/hoptrip/current` и `/opt/hoptrip/deployed-sha`.

Скрипты `scripts/deploy-production.sh` и `scripts/deploy-gateway.sh` установлены root-owned
как `/usr/local/sbin/hoptrip-deploy` и `/usr/local/bin/hoptrip-deploy-gateway`.
Их изменение в Git не меняет привилегированный обработчик автоматически: после проверки
обновить установленную копию административным SSH-доступом. При приватизации репозитория
нужно отдельно настроить доступ сервера к архивам. Контролировать свободное место;
автоматическое удаление release/backup в этот выпуск не входит.

## Откат и ограничения

При ошибке после остановки writers скрипт возвращает предыдущие образы приложения.
Миграции назад автоматически не откатываются. Применять только совместимые миграции;
разрушительные изменения требуют отдельного плана. Для ручного отката сохранены образы
`hoptrip-<service>:rollback-<time>` и `backups/deploy-<time>-<sha>/previous-source`.
Бэкап на этой же VM не заменяет offsite-копию. Восстановление БД выполнять отдельно,
в проверенную пустую базу, по `docs/operations.md`.

Пуши в `main` разрешают серверу запускать код репозитория. Не сливать недоверенный код.
Настройки партнёров этим механизмом не подтверждаются и не включаются автоматически.
