`sub_id=ht_probe_20260929_075733`, shorten=false, текущими project/marker.

пользовательского пути /go, уникального ID каждого клика или атрибуции бронирования.
Рабочие ссылки компонентов и tracking_param не менялись, записей в БД не добавляли.

## Подтверждённые способы

1. API `POST https://api.travelpayouts.com/links/v1/create` принимает
   `links[].sub_id` вместе с исходным `url`, `trs`, `marker` и `shorten`.
   Это документированный способ задать метку при генерации ссылки.
   Максимум 10 ссылок за запрос, 100 запросов в минуту на marker.
   [Контракт API ссылок](https://support.travelpayouts.com/hc/en-us/articles/25289759198226-API-for-Travelpayouts-partner-links).
2. Для коротких ссылок описано добавление или изменение `?sub_id=...`.
   Пример в документации использует tp.st. Эту инструкцию нельзя автоматически
   переносить на другой формат: HopTrip получает длинные ссылки tp.media/r.
   [Динамический SubID коротких ссылок](https://support.travelpayouts.com/hc/en-us/articles/12729746524050-How-to-dynamically-change-SubID-in-short-affiliate-links).
3. Допустимы латинские буквы, цифры и `_`, длина до 4096 символов.
   В Reports → Performance есть фильтрация и группировка по SubID.
   [Правила ID/SubID](https://support.travelpayouts.com/hc/en-us/articles/203955653-ID-and-SubID-Affiliate-marker-and-additional-marker).
4. Statistics API предоставляет `sub_id` и `external_click_id`; SubID поддерживает
   фильтр eq. Пример ответа содержит SubID с ведущей точкой, поэтому формат
   возвращаемого значения надо проверить на реальном отчёте, а не угадывать.
   [Контракт статистики](https://support.travelpayouts.com/hc/en-us/articles/360019864079-API-of-affiliate-programs-booking-statistics).

PLACEMENT_SUB_ID=hoptrip_web_deal. Каждый элемент запроса генерации содержит sub_id.

При отказе API действует прежняя политика: непроверенная ссылка не публикуется,
успешные предыдущие пакеты сохраняются. Блокировка pipeline и лимиты не изменены.

Добавлено 9 проверок: обновление отсутствующей/другой/пустой/дублирующейся метки,
отказ при потере SubID, неверных project/marker или маршруте в ответе.
Общий локальный результат: 194 passed, 5 PostgreSQL skipped; Ruff/mypy успешны.
Метка обозначает размещение, не посетителя: tracking_param остаётся None,
уникальные ID кликов не передаются. Результат развёртывания — blocker-resolution.md.

## Что это означает для существующего кода

- `services/partner_links.py` создаёт длинные ссылки (`shorten=false`) с постоянным sub_id.
  Текущая политика требует `tracking_param=None`; простое изменение поля программы
  приведёт к ошибке очередного обновления ссылок.
- `affiliate_adapters/stored.py` умеет подставлять query-параметр, но сам по себе
  этот механизм не подтверждает, что конкретный партнёрский формат его понимает.
- `api/affiliate.py` создаёт `ht-` + UUID hex. Дефис отсутствует в опубликованном
  наборе допустимых символов. Для будущего передаваемого ID подходит `ht_` + hex.
  Текущие записи менять не нужно: при tracking_param=None ID не передаётся партнёру
  и в AffiliateClick.tracking_id сохраняется None.
- Нынешняя команда статистики показывает агрегаты аккаунта. Она не запрашивает
  отдельные SubID и не выполняет сопоставление бронирований с кликами.

## Последовательность внедрения

Первый законченный этап — метка размещения, например `hoptrip_web_deal`, через
официальный API генерации. Это позволит выделить этот инструмент в отчётности;
одна такая метка не позволяет различать отдельные клики.

1. В отдельной проверке создать одну ссылку Aviasales с меткой, сохранив маршрут,
   даты, валюту и project/marker. Проверить ответ и целевой URL; не заменять все
   рабочие ссылки до приёмки этого формата.
2. Изменить валидацию и критерий «ссылка не изменилась», чтобы нужный SubID был
   частью проверяемого результата. Добавить тесты потери метки, неверного marker,
   изменения маршрута и отказа API. Сохранить общую блокировку pipeline.
3. Проверить переход и появление именно этой метки в отчётности. Сам HTTP 200
   от генератора не доказывает учёт клика или бронирования.
4. Для отдельных кликов выбрать и проверить документированный динамический формат
   либо генерацию через API с уникальным `ht_...`. Вариант с запросом API на каждый
   клик добавляет задержку и расходует квоту; его не включать без обработки отказов.
5. Проверить фактическое представление sub_id в ответе статистики и затем подключить
   точное сопоставление с сохранённым tracking_id. Не удалять ведущие символы
   произвольно; не приписывать агрегаты аккаунта конкретному клику.

Метки не должны содержать email, имя, IP или другие данные пользователя.
Покупка билета ради проверки не требуется. Передача уникального ID требует
отдельной проверки соответствия текущей модели согласия/раскрытия обработки данных.
