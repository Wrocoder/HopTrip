## Продуктовое решение

Расширить страницу перелёта блоком «Что посмотреть и чем заняться», подобранным
по городу и периоду пребывания. Покупка каждого предложения происходит у партнёра.
Первый запуск — небольшой проверенный каталог активностей; полноценная афиша
концертов, выставок и спорта требует источника датированных событий.

Разделять два сценария:

- «События в ваши даты»: концерт, матч, временная выставка с известными датами.
- «Музеи и развлечения»: постоянные объекты, экскурсии, аудиогиды, городские passes.
  Наличие продукта в каталоге не подтверждает свободные места в даты поездки.

В дальнейшем возможен обратный сценарий: пользователь выбирает событие,
а HopTrip подбирает перелёт. Это отдельный этап: текущее покрытие кеша перелётов
не гарантирует рейсы на произвольные даты события.

## Программы на скриншоте

Ставки ниже переписаны со скриншота, не являются гарантией выплаты за любой продукт.
Available и Generate links подтверждают доступность инструмента в показанном
кабинете, но не наличие API каталога, расписания, остатков или live-цен.

| Программа | Комиссия на скриншоте | Предлагаемая роль |
| --- | --- | --- |
| Tiqets | 3,5–8% | Первый кандидат для музеев и достопримечательностей |
| WeGoTrip | 6,64–41,5% | Аудиоэкскурсии; учитывать язык конкретного продукта |
| Klook | 2–5% | Кандидат для расширения каталога активностей после проверки нужных городов |
| Go City | 3,4–6% | Городские абонементы на несколько достопримечательностей |
| KKday | 1–5% | Дополнительный кандидат; сначала проверить европейское покрытие и инструменты |
| Welcome Pickups | 8–9% | Следующий этап: трансферы |

Приоритет Tiqets — продуктовая рекомендация для начала, а не результат сравнения
конверсий или полноты каталогов. Klook и KKday пока требуют отдельной проверки
ассортимента и доступа. Комиссия не должна определять порядок рекомендаций.

Travelpayouts описывает для Tiqets таблицу ID городов и Top 50 продуктов для
настройки виджетов. Это не полный каталог с наличием на даты.
[Документация Tiqets в Travelpayouts](https://support.travelpayouts.com/hc/en-us/articles/360010455179-Data-from-Tiqets).

Для WeGoTrip опубликован API городов, языков и продуктов. Полученные товарные URL
нужно преобразовывать в партнёрские ссылки через инструмент программы.
[Документация WeGoTrip](https://support.travelpayouts.com/hc/en-us/articles/360016170039-WeGoTrip-affiliate-program-API).

Go City продаёт passes на несколько достопримечательностей.
[Описание программы](https://www.travelpayouts.com/en/offers/go-city-card-affiliate-program/).
Welcome Pickups предлагает партнёрство по трансферам.
[Описание для affiliates](https://go.partner.welcomepickups.com/en/affiliates/signup/).

Для афиши кандидат — Ticketmaster Discovery API: поиск по месту, датам и категориям,
данные о площадке, часовом поясе и статусе события. Реальное покрытие выбранных
городов нужно измерить пробной выгрузкой. Доступ к данным не означает подключённую
партнёрскую монетизацию. Эта программа не показана на предоставленном скриншоте.
[Discovery API](https://developer.ticketmaster.com/products-and-docs/apis/discovery-manual/v2/),
[Discovery Feed и affiliate tracking](https://developer.ticketmaster.com/products-and-docs/apis/discovery-feed/).

## Что уже есть в коде

| Модуль | Что можно использовать |
| --- | --- |
| `apps/api/app/models/location.py` | Destination, координаты, timezone; заполненность надо проверить отдельно |
| `apps/api/app/models/deal.py` | Город, даты, компоненты, программа партнёра, признак обязательности |
| `apps/api/app/models/affiliate.py` | Независимые AffiliateProvider/AffiliateProgram, статусы и возможности |
| `apps/api/app/services/affiliate.py` | Проверка активной APPROVED-программы, разрешённого HTTPS host и ссылки |
| `apps/api/app/api/affiliate.py` | Серверный переход и фиксация клика |
| `apps/web/src/app/deals/[slug]/page.tsx` | Страница, где пользователь уже видит город и даты |

Нужные изменения и ограничения:

1. `/go/{slug}/{component}` выбирает запись по типу компонента через `db.scalar`.
   При нескольких ACTIVITY нет однозначной адресации. Новые переходы должны
   адресовать конкретное предложение по ID; старые flight URL сохранить рабочими.
2. AffiliateClick хранит deal/program/provider/type, но не ID конкретного компонента
   или продукта. Для измерения интереса к отдельным музеям и событиям нужны эти ID
   и placement. Для переходов со страницы города потребуется контекст без обязательного deal.
3. Для one-way `generate_flight_deal` ставит `trip_end = depart_at.date()`.
   Это техническое значение, а не известная продолжительность пребывания.
   Нужно предложить выбор дат, а до него показывать общий городской каталог.
4. TravelOffer ориентирован на перелёты: обязательные depart_at и original_price,
   авиационная история цен. Музеи без даты и события без известной цены не следует
   помещать туда с выдуманными значениями.
5. Pipeline напрямую создаёт TravelpayoutsDataProvider; sync_partner_links привязан
   к Aviasales и FLIGHT. Новые загрузчики и создание ссылок нужно реализовать отдельно.
6. DealComponentRead не содержит названия, изображения, места или расписания;
   UI всех компонентов использует одну CTA. Нужны отдельные DTO и карточки активностей.
7. hotel_price_pln в Deal — только поле. Генератор перелётов сбрасывает его в None
   и пересчитывает total как цену перелёта. Оно не является готовой интеграцией отелей.
8. DestinationAlias сейчас имеет code длиной 3: произвольные ID городов Tiqets и
   других поставщиков требуют отдельного сопоставления, а не использования IATA-поля.

## Предлагаемая модель

Добавить отдельный каталог активностей, сохранив существующую авиационную модель:

- `Activity`: название, категория, destination_id, площадка, координаты, описание,
  изображение и источник/условия его использования, язык, вид расписания.
- `ActivityOccurrence`: конкретный сеанс или период выставки, timezone, точность
  даты/времени, статус (в том числе отмена, перенос, неизвестная дата).
- `ActivityOffer`: поставщик и внешний ID, activity_id, при необходимости occurrence_id,
  программа, партнёрская ссылка, цена и исходная валюта, основание цены (от/за билет),
  наличие, время проверки и срок актуальности. Цена может отсутствовать.
- `ProviderDestinationMapping`: provider_code + внешний ID города → destination_id.

Одно событие может иметь несколько сеансов и продавцов. В первой версии допустим
один продавец и ручное сопоставление, но продукт не копируется в БД для каждого перелёта.
Рекомендации выбираются по городу и датам; ручной приоритет можно хранить отдельно.

Общие части для будущих услуг: реестр программ, проверка исходящих ссылок,
контекст поездки (город, аэропорт, даты, путешественники), учёт конкретного оффера
и места размещения. Предметные данные разделять: у отеля ночи/номер/гости,
у трансфера аэропорт/адрес/пассажиры, у страховки собственные параметры расчёта.
Отдельную сохраняемую Trip/TripPlan вводить, когда появится сохранение или сборка поездки.

## Подбор по датам и отображение

- Сопоставлять город по внутреннему ID и подтверждённому mapping, не по названию.
- Сравнивать события в часовом поясе назначения; обрабатывать переходы летнего времени.
- Для выставки проверять пересечение периодов, для концерта — конкретный сеанс.
- Даты вылета туда/обратно не гарантируют нахождение в городе весь первый/последний
  день. Без времени прибытия и трансфера не обещать, что пользователь успеет на событие.
- Неизвестный день/время показывать явно. Отменённые события исключать из рекомендаций;
  перенос обновляет дату и подбор. Sold out не выдавать за доступные билеты.
- Без проверки слотов CTA: «Проверить даты и цену». Общая ссылка на город имеет
  соответствующее название и не выдаётся за ссылку на конкретный билет.
- Сбой поставщика не блокирует перелёт; кешировать данные по городу/периоду,
  обновлять фоновыми заданиями с отдельными лимитами и допустимым сроком хранения.
- Не прибавлять необязательные активности к цене перелёта и не включать их комиссии
  в flight score. При отсутствии надёжного FX показывать исходную валюту.

На странице предложения разместить до 3–6 карточек после основного блока перелёта.
Польские названия блоков: «Wydarzenia w terminie podróży» и «Atrakcje i muzea».
Карточка: название, тип, фото при разрешённом использовании, дата или режим посещения,
место, известная цена и её основание, партнёр, CTA. Для аудиогида — язык.
Отдельные ссылки и бронирования; суммы описывают именно то, что в них включено.

## Порядок реализации и приёмка

1. **Пилот каталога.** Выбрать 3–5 городов по актуальному наличию перелётов/трафику.
   Подготовить по несколько проверенных Tiqets-продуктов, корректные ссылки,
   минимальную модель, адресацию по ID и блок на странице. При отсутствии feed
   допустима ручная подборка без неподтверждённых цен и обещаний наличия.
   Это первый релиз, но ещё не выполнение требования о полноценной афише.
2. **Афиша на даты.** Проверить реальный источник событий, покрытие городов и
   условия использования; добавить импорт, расписание и обновления отмен/переносов.
   Реализовать выбор периода для one-way и отдельную выдачу событий на даты поездки.
3. **Расширение.** WeGoTrip с фильтром языка; Klook/KKday при подтверждённой пользе
   каталога; городские passes. Затем трансферы, отели и страховки через общие
   правила партнёров и отдельные модели/адаптеры.
4. **Поездки ради события.** Поиск события → подходящие перелёты; только после
   проверки покрытия авиационных источников по нужным датам.

Проверки реализации: разные карточки ведут на разные правильные продукты;
истёкший/отозванный оффер не перенаправляет; соседний город не подмешивается;
one-way не выдумывает период; TZ и границы поездки корректны; отмена/перенос
обновляют рекомендации; отсутствие цены не превращается в ноль; сбой feed не
ломает перелёт; мобильный интерфейс работает; аналитика сохраняет текущие правила
согласия. Проверка редиректа и запись клика не подтверждают начисление комиссии.

Метрики: доля поездок с полезными рекомендациями, показы/клики по категориям,
подтверждённые продажи и доход отдельно по валютам, влияние на переходы к перелётам.
Отсутствие событий в источнике не описывать как отсутствие событий в самом городе.

## Что ещё нужно из кабинета

Для первого партнёра: ID программы/проекта, сгенерированная ссылка на конкретный
продукт, доступные Tools (links/widgets/API/feed), правила использования контента
и применимые ограничения рынка/канала. Секреты хранить вне Git и чата.
Проверить передачу дат, сохранение конкретного продукта после перехода и атрибуцию.
Наличие прямого API бренда не подтверждает его совместимость с Travelpayouts tracking.

В `blocker-resolution.md` есть старые незакрытые пункты, противоречащие более новым
записям об индексации и уведомлениях. При планировании запуска учитывать датированные
результаты; общую сверку этого исторического документа выполнить отдельно.
