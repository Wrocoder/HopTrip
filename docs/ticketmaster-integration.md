# События на страницах поездок — 2026-10-24

Реализация подготовлена и проверена локально. Production, серверный ключ и реальные
Telegram-отправки в этой задаче не менялись. Текущий подключённый источник — Ticketmaster.

## Каталог и расписание

`events-worker` обновляет каталог четыре раза в день: **00:00, 06:00, 12:00, 18:00
Europe/Warsaw**. Переходы зимнего/летнего времени обрабатывает календарный планировщик.
Первое заполнение выполняется отдельным запуском `--once`.

Миграция `0015_events_catalog` добавляет `events` и `event_sync_windows`.
Уникальность события: источник + внешний ID; повторная загрузка обновляет запись.
Хранятся нормализованные публичные поля, без исходных ответов API и секретов.

Загрузчик выбирает действующие предложения из Польши и поддерживаемые города
19 настроенных стран. Даты группируются в недельные интервалы; перекрывающиеся
поездки используют одну загрузку. Для one-way учитывается до 90 дней пребывания,
общий горизонт ограничен 365 днями. Страна, город и часовой пояс берутся из каталога.
Соседние города автоматически не добавляются.

Каждый период загружается целиком: до десяти страниц по сто записей; переполненная
неделя делится на меньшие периоды, вплоть до суток. Если сутки не помещаются в лимит
пагинации, период считается неполным. При ошибке или исчерпании бюджета прежние
события сохраняются. Отсутствующие в полностью загруженном периоде события скрываются.

Запросы идут последовательно с интервалом минимум 1,05 с. По умолчанию разрешено
1000 запросов за запуск и 4000 за UTC-день. Счётчик резервируется в БД до сетевого
запроса и переживает перезапуск. Самые давно проверявшиеся периоды обрабатываются
первыми. 401/403/429 останавливают текущий проход. При нехватке бюджета отчёт явно
показывает неполное покрытие; наличие worker не гарантирует полноту всех городов.
PostgreSQL advisory lock запрещает параллельные загрузки событий и независим от
блокировки перелётов. Незавершённый запуск отмечается INTERRUPTED следующим владельцем.

## Страница поездки

Публичный API читает только БД и не обращается к Ticketmaster. Для round-trip блок
запрашивает события автоматически при открытии страницы. Для one-way пользователь
указывает конец пребывания; даты и категорию можно изменить формой.

Сопоставление учитывает город и местные даты прилёта/обратного вылета, если известны,
иначе даты предложения. Максимум 31 день в одном запросе. События старше 18 часов
с момента проверки не показываются. Непроверенный период не выдаётся за успешную
пустую выдачу; неполное покрытие отмечается отдельно.

Отменённые, отложенные, offsale, тестовые события и неизвестные даты исключаются.
События до прилёта или после начала обратного вылета исключаются при известном времени.
Время дороги и продолжительность мероприятия не моделируются. Максимум 12 карточек;
усечение обозначается. Интерфейс переведён на PL/EN/RU/UK.

Ссылки принимаются только с ожидаемым publisher ID и разрешённым доменом Ticketmaster
в параметре `u`, без секретов и вложенных редиректов. Ссылка сохраняется без подмены
партнёрской программы; `rel="sponsored noopener noreferrer"`. Tracking не подтверждает
начисление комиссии. Изображения поставщика не копируются.

## Telegram

`scripts/notify-activity.py` использует существующий технический бот, чат и тему
из `/etc/hoptrip/monitor.env`, как для перелётов. Отдельный курсор `event_job_id`
не затрагивает курсоры перелётов и почты. После подтверждённой доставки курсор
сохраняется; при ошибке отправка будет повторена. Как и существующий транспорт,
сбой после приёма сообщения Telegram, но до записи курсора, может дать дубль.

Отчёт для SUCCEEDED/FAILED/INTERRUPTED содержит добавленные, обновлённые и скрытые
события, проверенные/запланированные периоды, ошибки, число запросов и длительность.
При первом подключении отправляется только последний завершённый запуск.
`EVENTS_MONITOR_ENABLED=true` в окружении host-monitor включает проверку контейнера
и отсутствия успешного обновления более 7 ч 30 мин; используется действующая логика
аварийных уведомлений и восстановления. Включать после первого заполнения.

## Выпуск и включение

В серверном окружении (секрет вне Git):

```text
EVENTS_ENABLED=false
EVENTS_SYNC_ENABLED=true
TICKETMASTER_API_KEY=<секрет>
TICKETMASTER_AFFILIATE_ID=7853869
EVENTS_COUNTRIES=AT,BE,CH,CY,CZ,DE,DK,ES,FI,FR,GB,GR,IE,IT,NL,NO,PL,SE,TR
EVENTS_MAX_AGE_HOURS=18
EVENTS_RUN_REQUEST_LIMIT=1000
EVENTS_DAILY_REQUEST_LIMIT=4000
EVENTS_HORIZON_DAYS=365
```

1. Выпустить проверенный commit обычным ручным процессом проекта. Обновить установленный
   `/usr/local/sbin/hoptrip-deploy` из `scripts/deploy-production.sh`: он не обновляется
   автоматически. Новая версия учитывает events-worker при сборке, остановке writers,
   запуске и откате. Секреты не передавать аргументами команд.
2. Применить миграцию штатным deploy. С новым окружением deploy запускает events-worker.
   Обновить host-копии `/opt/hoptrip/scripts/notify-activity.py` и `monitor.py` из выпуска:
   systemd использует эти пути, а не автоматически каталог нового release.
3. Из каталога выпуска выполнить первоначальное заполнение:

   ```sh
   docker compose -p hoptrip --env-file /opt/hoptrip/.env.production \
     -f docker-compose.yml -f docker-compose.production.yml -f docker-compose.domain.yml \
     --profile events run --rm --no-deps events-worker \
     python -m app.jobs.event_scheduler --once
   ```

4. Проверить EVENTS_SYNC в job_runs и фактическую доставку отчёта существующим
   hoptrip-activity.timer. Затем установить EVENTS_ENABLED=true и пересоздать API;
   включить EVENTS_MONITOR_ENABLED=true в `/etc/hoptrip/monitor.env`.
5. Проверить реальную страницу round-trip. Для отключения скрыть блок через
   EVENTS_ENABLED=false, а загрузку остановить через events-worker и
   EVENTS_SYNC_ENABLED=false; одновременно выключить EVENTS_MONITOR_ENABLED.

До выполнения этих шагов нельзя считать серверный сбор и Telegram подключёнными.
Подключение публичных социальных каналов — отдельная задача из social-publishing-plan.md.
