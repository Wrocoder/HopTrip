## Реализация

Использована основа `feature/email-alerts`: API регистрации, подтверждения,
управления и отписки, SMTP с проверяемым TLS, UI и существующая таблица deal_alerts.
Пакет перенесён локально в main выборочно. Digest worker и расписание из feature
ветки не переносились: это HT-13. Новые миграции не требуются.

Настройки: аэропорт, бюджет перелёта на человека, ночи, направление, диапазон
вылетов, только выходные, частота weekly/daily. Weekend соответствует вылету
в пятницу/субботу и возвращению в ближайшее воскресенье. Настройки сохраняются
в существующем JSON filters. Старые записи получают значения по умолчанию
weekly/false при разборе. Фактический отбор и доставка — отдельная HT-13.

PENDING не считается активной подпиской. Подтверждение выполняется POST после
действия владельца email; GET ничего не активирует. Ссылка подтверждения живёт
48 часов. Management-токен и confirmation-токен не взаимозаменяемы; токены
передаются в fragment и затем в POST body, не в query. Страницы noindex,
no-referrer, без аналитики и Drive. Отписка идемпотентна; работает и при
выключенной новой регистрации, если сохранён signing key.

Email нормализуется и уникален в БД. Повторный анонимный signup не меняет
активные настройки. Повторные письма ограничены сутками; есть общий суточный
лимит. Ошибка отправки оставляет PENDING, не выдаётся за активацию.
После ошибки SMTP повторная попытка возможна не ранее суток.

ALERTS_ENABLED=false по умолчанию. Без него /alerts показывает недоступность
и ссылку на каталог, не форму регистрации. Включение требует заполненного SMTP,
отправителя, signing key >= 32 символов и HTTPS origin (HTTP лишь localhost).
Параметры добавлены в env-примеры и environment только API в Compose.
Интерфейс честно сообщает, что доставка подборок ещё не запущена.

## Приёмка реального канала — 2026-10-12

После явного разрешения владельца scripts/check-alert-smtp.py отправил ровно
одно письмо с kontakt@hoptrip.pl на тот же ящик через настоящий send_alert_mail.
Письмо с пометкой TEST получено в INBOX; IMAP read-only/BODY.PEEK не менял
флаг прочтения. Токен извлечён из полученного письма, а не из заглушки транспорта.
Через API проверено: PENDING → подтверждение → ACTIVE → изменение бюджета
250 → 220, weekly → daily и weekend → false → сохранение → STOPPED.
Повторная отписка успешна; повторное подтверждение после отписки возвращает 410.

Проверка выполнена в отдельном одноразовом контейнере с текущим исходным кодом,
зависимостями образа hoptrip-api и SQLite в памяти. Production БД не подключалась.
Signing key теста временный; ссылки localhost из письма предназначены только
для автоматической проверки, нажимать их не требуется. Контейнер удалён после
завершения. На VM в /opt/hoptrip/checks/ht12 сохранены итог и маркер попытки,
блокирующий повторную отправку при случайном повторном запуске.

Доставка на внешние домены и публичный маршрут сайта этим тестом не проверялись.
Код HT-12 ещё не развёрнут в публичных сервисах, ALERTS_ENABLED=false.
Это завершение приёмки HT-12, а не запуск подписок для посетителей.

Планирование подборок, исключение дублей, очистка старых записей и расписание
нужно завершить в HT-13 перед запуском доставки. Массовые отправки сейчас отсутствуют.
